# Decisions

Decisions taken after the spec was written. Where they disagree with the spec, these win.

| # | Decision | Why |
|---|---|---|
| 1 | v1 means "works for the author": the Windows/Ubuntu RTX 4070 Ti desktop plus the Mac as a LAN client, ending at M3–M4. Public-only work (installers for every OS, signing, Flatpak, ROCm, Intel Mac/ARM, third-party catalogs, PyPI SDK, catalog signing, translations) moves to a later "1.0 public" milestone. Interfaces stay pluggable. | Eight milestones in three languages is too much for one part-time developer; build only for users that exist. |
| 2 | The everyday engine runs on **Windows**, on the same GPU as Unity. The Mac is mostly for web/mobile work, not games. | Sharing the GPU with Unity is the normal case: idle unload and the pause toggle are core features, not extras. |
| 3 | The core owns jobs, plan and durable state. The engine only executes stage batches and stores artifacts by hash. | One source of truth for what a job ran, across local, LAN and cloud providers. |
| 4 | M0 gate: write the acceptance checklist before running anything; run a cloud arm (Hunyuan3D 2.1 PBR, TRELLIS.2 on a rented 24GB+ GPU) on the same 20 images. Local passes → continue as specced. Only cloud passes → default texturing routes to cloud and the claim becomes "local where it fits". Neither passes → stop and revisit in six months. | Makes the gate decidable and separates "12GB is too small" from "the models are not there yet". |
| 5 | When "fully offline" conflicts with speed budgets, offline wins: the default `fit_mode` is `fit-first` (offload, tiling); the 90 s target is re-measured on that path. | Offline is a v1 goal; speed numbers are targets. |
| 6 | Local texture output is base color + baked normal + baked AO, with roughness and metallic as editable per-asset constants. "PBR" is used only for outputs from models that produce it (Hunyuan3D 2.1 Paint, TRELLIS.2). | Hunyuan3D-2 Paint produces delit RGB only; nothing local produces roughness or metallic. |
| 7 | v1 is image-in only; the input image carries the art style. LoRA loading and text-to-image leave v1. First post-v1 feature: text-to-image with a style LoRA. | Style is set in 2D; there is no LoRA ecosystem for the 3D models. |
| 8 | GLB only until M6; FBX arrives with rigging, through Blender. Jobs still make GLB only; the library exports other formats (decision 19). | glTFast handles static props; FBX matters only for retargeting rigged characters. |
| 9 | Apache-2.0 for Forja's own code. Adapters for restrictively licensed families fetch pinned upstream source at install time and never commit it here. | Hunyuan3D repositories ship code under the same territory-restricted license as the weights (confirm in M0). |
| 10 | The 90 s success target refers to the Mobile prop preset (there is no "Standard" preset). | Matches the budget table. |
| 11 | Superseded by 37: stages are no longer keyed by what the routed provider runs, and the core no longer asks each provider what it runs to key a job. | Keys existed for the stage cache, which is gone. |
| 12 | Built-in presets set budgets and stage types, never models. At submit each open stage gets a model: the job's override, then `[models.stages]` in config, then the highest `rank` among models ready on the first provider in routing order that has one (for a job with side views, first the model that reads the most of them: decision 17). A stage with no ready model refuses the job instead of falling back. Stub models are picked only with `models.stubs = true`. Optional stages (texture.match) are per-job switches. Benchmarks pin their models in their project config. | One set of presets that always runs the real models. Installing a better model upgrades every preset, and a placeholder never passes for a real asset. |
| 13 | Models install from the app through the engine's task API: system checks with a fix each (winget or the Visual Studio Installer on Windows, steps elsewhere), live steps and download progress, cancel, remove and repair. A fix installs software, so the engine runs one only for a caller on its own machine. Custom, restricted and non-commercial licenses need acceptance once per model, recorded with its time in the core's library. uv is found where the engine runs from (or installed by a fix) rather than downloaded by the core, until packaging (spec section 9). | Setup must not need the command line or the M0 README; the toolchain matters only at install time, and prebuilt wheels can later remove it without changing this flow. |
| 14 | The app never shows configuration as JSON and has no settings import or export. Settings shows only settings something reads, writes them to the user's config.toml without losing its comments, and says which layer a locked value comes from. Presets travel as YAML files (a project's `forja/presets/` goes with its repository); keys never leave the keychain; "Copy diagnostics" is the one export, with the home folder masked. | Settings belong to one machine (GPU, paths, which PC serves models), so an export would mostly copy wrong values, and an export file is how keys leak. |
| 15 | Another computer joins by pairing: the computer that shares its GPU serves the network over TLS with a self-signed certificate, shows a six-digit code (ten minutes, one use, five attempts), and the joining core trades it for a long-lived share token and pins the certificate's SHA-256. Tokens and API keys live only in the OS keychain; no API returns one (the UI shows the store and the last four characters), and the core's log redacts every value it has read. A new provider goes after `local` in `routing.priority`. LAN discovery is not built: people type the address the sharing computer shows. | Pasting a 48-character token and trusting a self-signed certificate are the two steps people get wrong; a short code over a pinned connection removes both without a certificate authority. |
| 16 | Forja is model agnostic across providers, including model hubs. A hub (fal.ai first) joins with an API key kept in the keychain; Forja's recommended models are added, and any other catalog model can be added when its OpenAPI schema maps onto a stage: one image in and a GLB out does shape and texture, an image and a mesh in does texture. A field per view (`front_image_url`, `back_image_url`...) or a list of images makes it a multi-view model (decision 17); one that requires a view runs only on jobs that have it. Hosted models are paid, so they run only when a stage is pinned to them (or `routing.allow_paid_fallback` is on); the price shows before queueing, and `[routing.budget_usd]` limits per image, day and month are enforced on recorded costs. When a model does several stage types, the later stages of those types are skipped (with the optional stages that refine them), and bake transfers the textured high-poly's colors onto the low-poly. Inputs go to the hub inline; results come back into the store. | One API key reaches many better models without code per model, while local stays the default and spending stays in the user's hands. |
| 17 | A job is still image-in (7), but its subject may come in several views: the front, plus `left` (the subject's left side, facing the image's left edge), `back` and `right`. Each other view gets its own copy of the stages that prepare the image (background removal, framing) and reaches only the stages whose model lists it in `views:` (a manifest field; a hosted model's view fields). Without side views every key stays what it was. A single image may also be a reference sheet of those views side by side: after background removal a built-in `views.detect` stage finds the separate figures, calls a row of two or more of similar height on one ground line a turnaround, and labels it front, side, back from left to right (the outline cannot tell a front from a back, nor which way a side faces). A larger render with the same outline replaces its view, and close-ups cut by a frame are left out. `views.split` then cuts each chosen view from the original image, painting neighbours over in the backdrop colour. The job's `sheet` mode says what happens when one is found: `ask` (the app) waits, in a `waiting` status that holds no slot and survives restarts, for the user to confirm or relabel; `split` uses the proposal; `keep` (the default, and the CLI's unless `--sheet split`) uses the image whole and only records it. | Concept and turnaround sheets are how characters reach a 3D artist; read whole, a sheet becomes a group of figures, and a single front leaves the back to guesswork. The proposal comes from the cut-out because the backdrop is gone there, and the user confirms it because front, back and side direction are conventions, not something the outline shows. |
| 18 | Everything the desktop app does is also a CLI command, through the same `/v1` endpoint: the CLI is a second client of the core, never a way around it, so validation, events and engine restarts behave the same from both. Each command declares the endpoints it calls, and a test fails when an endpoint is neither reached by a command nor listed as app-only with the reason (thumbnails the 3D viewer renders, the catalog picture relay, previews of a picked image, raw uploads, the file a drag carries out of the window, and the server-sent copy of the event stream). Keys and tokens reach the CLI on stdin. Commands whose effect must outlive them (`share code`, `generate --no-wait`, `daemon stop`) need a running core instead of starting one in-process. The core reads an asset's triangles, vertices, materials and LODs from its GLB, so assets made from the CLI carry them too. | Scripts, CI and remote shells get every feature, and one code path per feature keeps the app and the CLI from drifting apart. |
| 19 | The library exports finished assets to GLB, FBX, OBJ, glTF, USDZ, STL and .blend, one asset to a file or several into a folder, and can open one in Blender. GLB is a copy; every other format is converted by the user's own Blender (4.2 or newer: the `blender.path` setting, else found on PATH and where its installers put it), run in the background with factory settings so add-ons cannot change the files. FBX, glTF and .blend keep the LODs (FBX names make a LOD group in Unity and Unreal; .blend hides the lower ones); OBJ, STL and USDZ keep the full detail only, STL in millimetres. Open in Blender starts Blender as the user set it up, with the asset imported into a new unsaved file. Library cards (with the rest of a selection) and a handle on the asset page also drag out as GLB files, into a running Blender 4.2+ (which imports a dropped glTF), Unity or a folder: the core writes a named copy to a temporary folder, kept a day, before the drag begins. Deleting an asset removes it and the job that made it from the library; files exported from it stay, and the next sweep of the store removes their bytes (decision 37). | Assets leave Forja for many tools, and Blender already reads and writes all of these formats well; writing them in the core would need cgo or a Go reimplementation of each. Blender is optional, so GLB never depends on it. A deleted generation is often regenerated with other settings, which the cached stages make fast. |
| 20 | Superseded by 37: there is no stage cache to limit, so `general.cache_max_gb`, `forja cache` and Settings' Cache section are gone; the store's leftovers are swept instead. | The limit only bounded the cache. |
| 21 | There is no Unity editor package. Forja reaches Unity, like every other engine, only through its exports: GLB, and FBX, glTF or .blend through Blender (decision 19). The M6 gate becomes: a generated character exports rigged, with LODs, and imports with an armature and no manual steps. Generating animation stays after 1.0. | The library's exports already land in Unity; an editor package would be a second product to keep up for one engine. |
| 22 | `forja bench` runs a versioned YAML suite as ordinary jobs that make no asset. A warm run first loads the models with one unmeasured image per preset; `--cold` unloads them before each image. Budgets live in the suite. `forja bench compare` fails (exit 6) when a value grows more than `bench.threshold_pct` (10) and past the noise floor (`bench.min_seconds`, `bench.min_vram_mb`); a newly failed sample always counts. The CLIP quality proxy waits until it can ship as an optional model-backed stage. | Measure the real pipeline, never a second one, without touching the user's library; a 20 ms stage at 30 ms is noise, not a 50% regression. |
| 23 | Policies order the providers that can run a model stage: `cheapest` by expected cost, `fastest` by the median measured time of that stage, model and provider; ties and unknowns keep priority order, and built-in stages keep priority order among providers that have them. A pinned model runs on the first provider where it is ready. When a provider cannot be reached or a stage runs out of memory, the failed stages are planned again without it, under the same rules: never to a paid provider unless `routing.allow_paid_fallback` is on, never to another paid provider for a stage the failed one billed, never away from a provider a stage was routed to explicitly. A provider that answered (any status below 500, or a job that ran and failed) is not unreachable. What succeeded is reused, and each move is kept on the job and shown in the app and the CLI. | A stage should run where it is cheapest or fastest only among providers the user already trusts, and a provider that drops out mid-job should cost a retry, not the job. |
| 24 | `[prices]` is the user-editable price table, with RunPod defaults from the spec; an entry named after a hosted model replaces the price its vendor reports, and a time price on a model replaces its provider's rate instead of adding to it. Spending limits are a hard stop for every paid provider: checked at submit counting queued jobs, again before each paid batch, and a batch billed by the second is metered and stopped at the limit. A cost is recorded whenever the provider billed, failures included. Estimates before queueing take time from measured history and cost from the table. | Vendor prices change, so the user owns the table; a limit that several queued jobs can pass together, or that ignores a billed failure, is not a limit. |
| 25 | Engine images are `forja-engine:<version>-<cuda line>` (`cpu`, `cu124`) with no weights; envs, weights and the store live on a volume. Per-model baked images are `-<model>`, the RunPod worker is `-runpod`. Users build and push them to their own registry. Serverless artifacts move by hash through the endpoint's network volume (RunPod's S3 API; on Modal a CPU gateway that serves `/v1` and wakes the GPU only for runs); without the volume key they ride inline as base64, up to about 7 MB each way. A ComfyUI workflow is copied beside config.toml and keyed by its content hash. | One small image per torch lane, weights that persist between cold starts, each byte crossing once after a HEAD by hash, and no Modal-specific core code; an edited workflow never reuses outputs cached from the old one. |
| 26 | A Mac runs locally only what its pinned upstream runs on Apple GPUs: Hunyuan3D-2mv shape (experimental until the Apple Silicon workflow passes on the maintainer's Mac) and BiRefNet on the CPU. TripoSG and Hunyuan3D-2 Paint stay CUDA-only and route to another provider. A family lane may install only some of its models (build and smoke per lane). The Apple GPU's budget is Metal's recommended working set less the usual reserve. | TripoSG imports diso's CUDA-only marching cubes at module level and Paint needs a CUDA rasterizer, while 2mv's shape pipeline is plain torch; unified memory has no VRAM total. |
| 27 | Packages are signed only when certificates exist: Windows with Authenticode from `WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD`, macOS with a Developer ID from `CSC_LINK`/`CSC_KEY_PASSWORD` and notarized when `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD` and `APPLE_TEAM_ID` exist. Otherwise Windows builds are unsigned and Mac builds are signed ad hoc without the hardened runtime. macOS ships arm64 and x64 DMGs and zips (macOS 13+). | Certificates cost money and are not bought yet (spec section 18); Apple Silicon refuses unsigned apps, and electron-updater updates a Mac from the zip. |
| 28 | The root `VERSION` file is the one version of the app, the core, the engine, its model families and the adapter SDK; `make version V=` writes it everywhere and CI checks they agree. The engine API keeps its own version. `vX.Y.Z` tags are stable releases; `-rc.N` and `-beta.N` are prereleases on the beta channel. A stable tag needs the GPU nightly and the bench gate green on its commit, and the bench results attached to a stable release are the next baseline. GPU workflows run only on the maintainer's self-hosted runner, never for pull requests, and only when the repository variable `FORJA_GPU_RUNNER` is `true`. | Spec section 15 asks for one number and gated releases; a single file cannot drift, and forks or a repository without the runner must skip GPU jobs instead of queueing forever. |
| 29 | Shipped dependencies are scanned for licenses in CI: strong copyleft (GPL, AGPL, SSPL, EUPL, OSL) fails in Python and JS, and any restricted or unknown license fails in Go, whose binary links statically. Catalog manifests must pass the strict schema in `catalog/schema/` (SPDX id, commercial flag, terms URL unless a stub, pinned revisions and hashes, no unknown fields); `catalog/index.json` is generated and committed, and signing it comes later. | Spec section 18's license traps, and pinning enforced by a check instead of convention. |
| 30 | The adapter contract ships as `forja-engine-sdk` (import `forja_sdk`, in `engine/sdk/`), standard library only; `forja_engine.sdk` re-exports the same objects and the engine pins the SDK exactly. `forja-sdk test` is the conformance suite: determinism means byte-identical outputs for the same inputs, params and seed, and the VRAM check fails when the measured peak passes the manifest's `vram_gb` by more than 25%. A model package (`family.yaml`, `manifests/`, an adapter package) listed in `engine.manifest_dirs` installs like a bundled family, under a name no bundled family, `stub` or `builtin` uses. | Third-party adapters depend on the contract alone, without the engine's dependencies; this is the M7 gate, since a manifest folder could not bring its own family before. |
| 31 | Rigging is an optional per-job stage on the Hero character preset, off by default, after bake and before LODs: the shipped low-poly is what gets rigged, and every LOD shares its one skin. Jobs still make a GLB (now skinned) plus a skeleton profile; FBX, glTF and .blend keep the armature through the library's Blender export (decisions 8 and 19). UniRig is the rig model for 12 GB cards; SkinTokens ranks above it but needs 14 GB, so it is remote-only there. Where flash-attn has no wheels (Windows), the rig families run the same attention on PyTorch's own kernels, and flash-attn is built only on Linux through marker-gated build entries. | Props need no rig; rigging what ships keeps UVs and LODs consistent. UniRig fits the reference PC (about 8.7 GB peak), and compiling flash-attn on Windows is impractical while the stand-in matches it within fp16 precision. |
| 32 | Humanoid bones are named as Unity's HumanBodyBones (also VRM's humanoid names), Y up, facing +Z, the character's left at +X. A predicted skeleton missing any of the 15 required bones is `generic`. The engine renames the mapped bones and keeps the predicted names in the profile's `bone_map`; the core and the viewer recognise a humanoid by its bone names, so it survives tools that drop glTF extras. | The retargeting in Unity and Unreal maps these names by itself, which is what "no manual steps" needs. |
| 33 | Blender-backed stages (`mesh.remesh`, `mesh.uv.smart`) run in the engine with the engine machine's Blender 4.2 or newer: `FORJA_BLENDER` (the core passes `blender.path` to the engine it starts), else PATH and the installers' locations. Blender runs as a separate process, in the background with factory settings, and is never linked. `/v1/info` offers these stages only where Blender is found, versioned with its version, and lists the others under `unavailable` with the reason; a job no provider can run is refused with it, and the app greys out the switch. Quad remesh uses Blender's QuadriFlow, which is not deterministic for a seed: a re-run makes other quads. | Stages run where the engine is, possibly another computer, and Blender is already the optional dependency for exports, so there is nothing new to pin or ship; a different Blender makes different quads, so its version is part of the stage's. |
| 34 | An optional stage may say `replaces: <stage>`: while it is on, that stage is dropped, its readers read the replacement, and the replacement takes its params. Quad remesh replaces decimation, off by default, on Environment piece (keeping sharp edges) and Hero character, within the same triangle budget. Smart UV Project is an optional UV stage before painting, and painters keep the UVs a mesh brings. | Remeshing is an alternative to decimating, not a refinement of it, and must keep the preset's budget and the user's overrides of it. |
| 35 | The bake writes MikkTSpace tangents (splitting vertices where needed), measures its cage from the meshes (twice the 95th percentile of the high-poly's distance, 0.3–5% of the diagonal), takes 4 samples per texel, bakes a ring around each island's seams and fills the rest of the gutters from island edges, and smooths AO only within islands. | Blender, Unreal and Unity recompute MikkTSpace, so maps must be baked in it to read the same everywhere; a fixed 2% cage picked up nearby surfaces on characters (hero normal error 4.23° → 0.49°, at 2.5× the speed). |
| 36 | A project's `forja.toml` sets only what a project is for: `[project]`, `[routing]` stages, priority and policy, `[models]` and `[presets]`. `[engine]`, `[blender]`, `[general]`, `[[providers]]` and `[prices]` there are ignored with a warning, a project's spending limits count only when stricter than the user's, and it can switch paid fallback off but never on. Model packages come from the user's own `engine.manifest_dirs`, not from a project. The local engine runs in the data folder with Windows' current-folder program search off, and finds Blender only in absolute PATH folders. | A project file arrives with a cloned repository or an unzipped pack: it must not start programs (an engine command, a Blender, an adapter) or let paid providers spend more than the user allows, and running `forja` inside such a folder must not run a program planted there. |
| 37 | There is no stage cache: every job runs every one of its stages, and nothing carries over from one job to the next. Within one run of a job, work it already did is not sent again: the background removal run while looking for a sheet of views serves the job's own stages, and a job that waited for the user's answer cuts its views from the cut-out it recorded. When the core starts, after the last running job ends and after an asset is deleted, the core removes the store's files the library no longer keeps (every asset's GLB, thumbnail and input, every job's images, all that an unfinished job references), except those stored within the last hour; there is no setting. | Reuse surprised: the same image again finished at once with no way to start over, and clearing the cache kept whatever the last hour used. Until reuse is something a job asks for, every run is a fresh one. Without the cache, a finished job's intermediates are leftovers, so they go once no job runs; the hour keeps an image picked but not yet submitted, and another computer's run on a shared engine, from losing a file. |
| 38 | The catalog adds the 2026 open models that beat its own: Pixal3D for shape (one image, and a multi-view model for side views), TRELLIS.2 for shape and TRELLIS.2 Paint for texture, all MIT and ranked above TripoSG, Hunyuan3D-2mv and Hunyuan3D-2 Paint. Tripo P2 joins fal's recommended models. A model's weights may come from several pinned sources (`weights.extra`: other Hugging Face repositories, or one HTTPS file checked by sha256), a family may fetch more pinned source archives (`upstream.extra`), and a build entry may start with `--no-deps`. Adapters build these pipelines from local files only, never with upstream's from_pretrained, which reaches the Hub and loads RMBG-2.0 (non-commercial, remote code) to cut out a background Forja already removed. Where a painter makes roughness and metallic maps, texture.match and the bake keep them as the ORM map's G and B (refines 6). Pixal3D runs with a fixed narrow field of view (`fov_degrees`, 11.5°) instead of upstream's MoGe-2 estimate, and stops once the shape is decoded. | Installing a better model upgrades every preset (decision 12), and MIT terms take the side-view path out of the territory-limited Hunyuan license where Pixal3D runs. Their ranks and memory figures come from upstream until the M0 bench measures them on the reference card. References for game assets are mostly drawn without perspective, and MoGe would bring a second geometry model and an unpinned dependency tree. |
| 39 | A family may say which operating systems it can be built on: `os: [linux]` in its `family.yaml` (`linux`, `windows`, `macos`; absent means wherever its lanes exist). Elsewhere its models are reported like models with no device here (`fit: unsupported`, no `runs_on`), their `runs-here` check says "<model> can only be installed on Linux: run it on another computer or a cloud GPU", and an install is refused with that sentence before anything is fetched. Pixal3D sets it: NATTEN does not build on Windows. | A lane says which torch a family uses, not where its extensions compile, so a Windows PC with an NVIDIA GPU was told Pixal3D fits: first-run Setup recommended a 26 GB install that failed at the build. No response changes shape, so the core and the app need nothing new to stop offering it. |
| 40 | Number settings have ranges the core enforces (`engine.idle_unload_minutes` 0 to 10080 with 0 meaning never, `engine.vram_reserve_gb` up to the detected card, spending limits 0 to 1,000,000), `blender.path` accepts only a program named `blender`, and engine settings restart the engine once, when nothing uses it. A config folder moved with `FORJA_CONFIG_DIR` writes its keys to a keychain group of its own (the default folder keeps `forja`) and still reads the ones saved under `forja` before. | A typo such as 1e20 reached config.toml and read back negative, any file typed as Blender's path was run, every edit of an engine number stopped a warm engine, and two data folders on one account overwrote each other's keys. |
| 41 | `texture.match` projects every reference view it is given, not only the front: the job's `left`, `back` and `right` views reach it as inputs tagged with their view (the core lists them in `engineapi.BuiltinViews`, as a model's manifest lists its `views`), each is fitted to its own camera around the front's yaw, and each is blended with the front's feathers and visibility test. The front goes last, so it wins where two views see a texel and the others fill what it cannot see. A side view's label is a convention nothing in its outline can check, so both side views are fitted facing both ways and each is used the way it fits; one used opposite to its label is logged and reported in the result. A view whose fit stays under `min_iou` is skipped and logged. Colors are still learned from the front alone. | The back and sides of an asset kept the painter's blurry texture even when the job had sharp references for them, and sheets drawn by other people often swap the two sides. |
| 42 | LODs are decimated on the position-welded LOD0 and their UVs rebuilt per island: one output vertex per (position, UV island), its UV taken from the closest LOD0 triangle of that island. | Simplifying the seam-split mesh treated every UV seam as a border and collapsed each side independently, cracking the LODs open (982 open edges at the first level of a real asset); welding keeps them closed at the same triangle count, and per-island vertices keep the seams sharp. |
| 43 | Hunyuan3D-2 Paint seeds its multiview diffusion with the job's seed and upscales each 512 px view 4x with Real-ESRGAN x4plus (BSD-3-Clause, an in-tree RRDBNet) before upstream resizes it. The file is a pinned `weights.extra` entry marked `optional: true`: install and repair fetch it, a failed download does not fail the install, and a model installed without it stays ready, paints unsharpened and says so in the stage note. | Upstream fixed the seed at 0, so regenerating never changed the paint, and left its super-resolution step commented out, so a 2K texture carried 512 px of detail per view. The weight is optional so a file added later does not break existing installs. |
| 44 | `texture.match` projects the front from the background-removal cut-out, framed like the reference at `min(reference_size, natural size)` px (`reference_size` defaults to 2048), instead of the 1024 px framed copy. The preset gives the stage the cut-out as a third input, untagged. The camera fit, the color learning and the side views keep the framed image, and a cut-out that is absent, not larger, or not the same silhouette is ignored. The alignment's block and radius grow with the picture above 1024 px. `framing` drops parts of the matte under 0.05% of the largest part's area before cropping (refines 41). | A 2K texture got a 1K image projected onto it even for a 4K picture. Raising the `frame` size would send the larger image to remote and hosted models too, and one stray fleck of matte shrank the subject in the frame. |
| 45 | Mobile prop and Environment piece have an optional "Paint a denser mesh" stage (`dense`, off by default): a 40,000-triangle decimation of the high-poly that the painter paints instead of the low-poly. The bake takes a third mesh input, the unpainted low-poly; when it has fewer triangles than the first mesh, the first only gives its colors, and the bake samples them (and the painter's metallic-roughness map) onto the low-poly's UVs with its own rays from the same cage. Otherwise the bake is unchanged. | Painters condition on renders of the mesh they are given and are tuned for tens of thousands of faces, so detail painted on a 5,000-triangle mesh cannot line up with the detail the bake takes from the high-poly. A switch, because the gain has not been measured on real painters and it costs time in a preset with a 90 s budget. |
| 46 | A plan says when the models it picks do not read a job's side views. Each model stage that reads the prepared reference image (shape, texture) carries `unread_views`, the job's views its model ignores, and `read_by`, the best model that reads more of them: listed by a free provider, not ready, fitting there, ranked by views read, then rank, then id. The job still runs and the pick is unchanged (12 stands). The CLI prints it under `--dry-run` and `--estimate`; Generate shows it under the models, and the card that confirms a sheet of views shows it for the views chosen there, each with a way to the Models screen. | Jobs with a full turnaround were shaped from the front alone when only a front-only shape model was installed, and nothing said the side views had been dropped. |
| 47 | Stages report what they measured about their output as `StageOutput.metrics`, finite numbers under snake_case names (engine API 1.9). The core keeps them with the output and words them once, in `internal/quality`, for the CLI, the app and `forja bench`. | 48 | An asset's roughness and metallic can be set per material after generation. Materials are the up to six dominant colors of the base color texture (deterministic k-means in CIELAB on a 256 px copy; colors under ΔE 10 merge, clusters under 1% fold), found again the same way each time. The core writes one roughness and metallic per material into the metallic-roughness map (G and B, R kept, borders blurred), sets the factors to 1, and replaces the asset's GLB in place (`PUT /v1/assets/{id}/materials`, `forja assets materials --set`); the old GLB goes at the next sweep.
