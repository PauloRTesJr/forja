# Decisions

Decisions taken after the spec was written. Where they disagree with the spec, these win.

| # | Decision | Why |
|---|---|---|
| 1 | v1 means "works for the author": the Windows/Ubuntu RTX 4070 Ti desktop plus the Mac as a LAN client, ending at M3–M4. Public-only work (installers for every OS, signing, Flatpak, ROCm, Intel Mac/ARM, third-party catalogs, PyPI SDK, catalog signing, translations) moves to a later "1.0 public" milestone. Interfaces stay pluggable. | Eight milestones in three languages is too much for one part-time developer; build only for users that exist. |
| 2 | The everyday engine runs on **Windows**, on the same GPU as Unity. The Mac is mostly for web/mobile work, not games. | Sharing the GPU with Unity is the normal case: idle unload and the pause toggle are core features, not extras. |
| 3 | The core owns jobs, plan, durable state and the stage cache index. The engine only executes stage batches and stores artifacts by hash. | One source of truth for "was this computed?" across local, LAN and cloud providers. |
| 4 | M0 gate: write the acceptance checklist before running anything; run a cloud arm (Hunyuan3D 2.1 PBR, TRELLIS.2 on a rented 24GB+ GPU) on the same 20 images. Local passes → continue as specced. Only cloud passes → default texturing routes to cloud and the claim becomes "local where it fits". Neither passes → stop and revisit in six months. | Makes the gate decidable and separates "12GB is too small" from "the models are not there yet". |
| 5 | When "fully offline" conflicts with speed budgets, offline wins: the default `fit_mode` is `fit-first` (offload, tiling); the 90 s target is re-measured on that path. | Offline is a v1 goal; speed numbers are targets. |
| 6 | Local texture output is base color + baked normal + baked AO, with roughness and metallic as editable per-asset constants. "PBR" is used only for outputs from models that produce it (Hunyuan3D 2.1 Paint, TRELLIS.2). | Hunyuan3D-2 Paint produces delit RGB only; nothing local produces roughness or metallic. |
| 7 | v1 is image-in only; the input image carries the art style. LoRA loading and text-to-image leave v1. First post-v1 feature: text-to-image with a style LoRA. | Style is set in 2D; there is no LoRA ecosystem for the 3D models. |
| 8 | GLB only until M6; FBX arrives with rigging, through Blender. | glTFast handles static props; FBX matters only for retargeting rigged characters. |
| 9 | Apache-2.0 for Forja's own code. Adapters for restrictively licensed families fetch pinned upstream source at install time and never commit it here. | Hunyuan3D repositories ship code under the same territory-restricted license as the weights (confirm in M0). |
| 10 | The 90 s success target refers to the Mobile prop preset (there is no "Standard" preset). | Matches the budget table. |
| 11 | A stage's cache key includes what the routed provider runs for it: a built-in's adapter version (`/v1/info` `stages`), or a model's `adapter_version`, weights revision and family upstream sha256 (`/v1/models`). Jobs are routed at submit and keyed when they start, which may start the local engine even for a fully cached job; a provider that cannot answer is keyed by its last answer in this session. | The provider is the only one that knows what it runs. A fixed adapter, new weights or new upstream code must never reuse outputs cached by the old ones, and a global key bump recomputes everything. |
| 12 | Built-in presets set budgets and stage types, never models. At submit each open stage gets a model: the job's override, then `[models.stages]` in config, then the highest `rank` among models ready on the first provider in routing order that has one. A stage with no ready model refuses the job instead of falling back. Stub models are picked only with `models.stubs = true`. Optional stages (texture.match) are per-job switches. Benchmarks pin their models in their project config. | One set of presets that always runs the real models. Installing a better model upgrades every preset, and a placeholder never passes for a real asset. |
| 13 | Models install from the app through the engine's task API: system checks with a fix each (winget or the Visual Studio Installer on Windows, steps elsewhere), live steps and download progress, cancel, remove and repair. A fix installs software, so the engine runs one only for a caller on its own machine. Custom, restricted and non-commercial licenses need acceptance once per model, recorded with its time in the core's library. uv is found where the engine runs from (or installed by a fix) rather than downloaded by the core, until packaging (spec section 9). | Setup must not need the command line or the M0 README; the toolchain matters only at install time, and prebuilt wheels can later remove it without changing this flow. |
| 14 | The app never shows configuration as JSON and has no settings import or export. Settings shows only settings something reads, writes them to the user's config.toml without losing its comments, and says which layer a locked value comes from. Presets travel as YAML files (a project's `forja/presets/` goes with its repository); keys never leave the keychain; "Copy diagnostics" is the one export, with the home folder masked. | Settings belong to one machine (GPU, paths, which PC serves models), so an export would mostly copy wrong values, and an export file is how keys leak. |
| 15 | Another computer joins by pairing: the computer that shares its GPU serves the network over TLS with a self-signed certificate, shows a six-digit code (ten minutes, one use, five attempts), and the joining core trades it for a long-lived share token and pins the certificate's SHA-256. Tokens and API keys live only in the OS keychain; no API returns one (the UI shows the store and the last four characters), and the core's log redacts every value it has read. A new provider goes after `local` in `routing.priority`. LAN discovery is not built: people type the address the sharing computer shows. | Pasting a 48-character token and trusting a self-signed certificate are the two steps people get wrong; a short code over a pinned connection removes both without a certificate authority. |
| 16 | Forja is model agnostic across providers, including model hubs. A hub (fal.ai first) joins with an API key kept in the keychain; Forja's recommended models are added, and any other catalog model can be added when its OpenAPI schema maps onto a stage: one image in and a GLB out does shape and texture, an image and a mesh in does texture. Hosted models are paid, so they run only when a stage is pinned to them (or `routing.allow_paid_fallback` is on); the price shows before queueing, and `[routing.budget_usd]` limits per image, day and month are enforced on recorded costs. When a model does several stage types, the later stages of those types are skipped (with the optional stages that refine them), and bake transfers the textured high-poly's colors onto the low-poly. Inputs go to the hub inline; results come back into the store. | One API key reaches many better models without code per model, while local stays the default and spending stays in the user's hands. |
